# 交易智能体交付手册

> 版本：P5 + 无人值守交付版（2026-10-20）
> 本文是运行手册：怎么跑、怎么判断它是否正常、出事怎么办、接实盘还差什么。

## 一、交付能力总览

| 能力 | 状态 | 说明 |
| --- | --- | --- |
| 模拟盘撮合 | ✅ | 保守成交：限价保护、涨跌停校验、无行情不猜测 |
| 决策与裁决 | ✅ | 模型建议 → 策略规则包逐条裁决，拦截原因全部落库 |
| 账本三不变量 | ✅ | 冻结资金、可用资金、冻结股数三条对账，drift=0 |
| 持仓防守线 | ✅ | 止损 / 硬止损 / 分级止盈 / 移动止损，只认 kill_switch，不调模型 |
| 自动循环 | ✅ | 认知 → 选股 → 裁决 → 执行，闸门分层记录 |
| 日亏 / 连败熔断 | ✅ | 三处同写（当日状态 + 门控 + 循环记录），解除必须给理由 |
| 复盘与经验 | ✅ | 只认已平仓事实，样本 <30 不输出胜率结论 |
| 业绩归因 | ✅ | 胜率 / 盈亏比 / 期望值 / 逐日曲线 / 按标的与离场原因分桶 |
| 交易日历 | ✅ | 法定节假日不跑循环、不生成复盘 |
| 日终委托作废 | ✅ | 跨收盘挂单作废并释放冻结；作废前先向通道撤单 |
| 运行事件流 | ✅ | 熔断、降级、自愈、日终清理全部落 `trading_events` |
| 健康自检 | ✅ | `GET /api/v1/trading/health`，critical 返回 503 |
| 告警外发 | ✅ | 企微/钉钉/webhook + 文件兜底，冷却合并，投递结果落库可查 |
| 按天回放 | ✅ | `GET /api/v1/trading/timeline?day=` 聚合六类记录成一条时间线 |
| 故障自愈 | ✅ | 账本自动对账修复；连续失败 3 轮自动降级暂停买入 |
| 通道契约 | ✅ | 异步回报幂等落账、撤单退避重试、超量回报截断告警 |
| 实盘通道 | ⛔ | 有意未接。契约与账本已就绪，见「五、接实盘还差什么」 |

## 二、运行方式

### 一条命令（推荐，含前端）

```bash
cd frontend && npm run build          # 只需在改前端后执行一次
node scripts/trading-agent.mjs --web   # 编译后端 + 守护 + 托管前端
```

打开 `http://127.0.0.1:20073/#trading` 即是完整交易页，后端在 `127.0.0.1:20081`。
静态托管只读，不代理 API——前端直接请求后端，少一层排查面。

### 守护模式（只跑后端）

```bash
node scripts/trading-agent.mjs            # 编译 + 启动 + 守护
node scripts/trading-agent.mjs --no-build # 跳过编译
```

守护进程职责：健康轮询（30 秒）、崩溃自动重启（指数退避至多 5 分钟）、连续 5 次不健康重启、日志轮转（5MB × 3 份）。日志在 `.runtime/trading-agent.log`。

### 手动模式

```bash
cd backend && go build -o bin/easy-stock-server.exe ./cmd/server
A_STOCK_ADDR=127.0.0.1:20081 ./backend/bin/easy-stock-server.exe
cd frontend && npm run dev   # 交易页：http://127.0.0.1:20073/#trading
```

## 二·五、配置告警（无人值守必做）

没有告警出口时，系统出问题只会写进数据库和页面——人不在电脑前就等于没通知。
这是无人值守最容易失效的一环，所以它被单独列成一节。

```bash
# 企微 / 钉钉机器人：贴一个 URL 就能用
export A_STOCK_TRADING_ALERT_WEBHOOK="https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxx"
export A_STOCK_TRADING_ALERT_FORMAT=wecom        # wecom | dingtalk | json（默认 json）

# 文件出口是兜底，默认就开着，落在日志目录 trading-alerts.log
export A_STOCK_TRADING_ALERT_LOG="D:/easy-stock-main/.runtime/trading-alerts.log"

# 临时关闭全部外发
export A_STOCK_TRADING_ALERT_OFF=1
```

**配完必须验证**：页面「告警投递」面板点「发送测试」，或

```bash
curl -X POST http://127.0.0.1:20081/api/v1/trading/alerts/test
```

返回 `{"delivered":["webhook","file"]}` 才算通。启动日志也会打出
`event=trading_alerts_ready channels=webhook,file`；若打出
`trading_alerts_no_channel`，说明一个出口都没配上。

### 收敛规则

同一 `kind + symbol` 的告警有冷却窗口，避免把真正的问题淹掉：

| 等级 | 冷却 | 说明 |
| --- | --- | --- |
| critical | 10 分钟 | 严重问题反复提醒，但不会每轮循环都喊一次 |
| warning | 60 分钟 | 积压、熔断这类状态不值得每分钟推 |

- 冷却期内的同类告警**只计数不外发**，冷却结束补发一条并带上「期间另有 N 条已合并」「此问题仍在持续」。
- 严重度升高（warning → critical）**立即突破冷却**，不合并。
- 投递全部失败时不占用冷却，下一条同类告警立刻重试——没送达等于没发过。
- 全部出口失败会记 `failed` 并写失败原因，健康条也会出现 `alerts.delivery_failed`。

### 什么会触发告警

warning 及以上事件全部外发：账本漂移、连续失败降级、熔断、挂单积压、通道错误。
另外 `autopilot.recovered` 与 `ledger.drift_healed` 虽然是 info 也会发——
人收到"出问题了"之后，最想知道的是"好了没有"。

## 二·六、按天回放

```
GET /api/v1/trading/timeline?day=2026-10-20
```

把当天的循环、计划、裁决、委托、事件、复盘按时间摊平成一条线，页面「时间线回放」面板可直接切日期。
回答"那天为什么没买""这笔单是哪一轮下的"时先看它，不用再去五张表里各查一遍。

摘要里带 `model_calls` 与 `total_tokens`——自动交易一天花多少思考成本，可查而不是靠账单反推。
`notes` 非空表示某张表读失败，**这条线不完整**，不要据此下结论。

## 三、怎么判断系统是否正常

### 一眼看：页面健康条

交易页顶部「运行正常 / 注意 / 需要立即处理」：

- **绿色**：什么都不用做。
- **黄色**：系统还在工作，但有需要知道的事（熔断中、已降级、挂单积压）。
- **红色**：账本漂移、连续失败 ≥3 轮、心跳超时——必须立刻处理。

### 接口级

```
GET /api/v1/trading/health
```

- `200` = healthy / warning；`503` = critical。外部监控只看状态码即可。
- `issues[]` 每项含 `code`（稳定标识）与 `message`（人话）。

### 关键判定规则

| 条件 | 等级 | 含义 |
| --- | --- | --- |
| 账本 drift > 1 分 或股数漂移 | critical | 钱或股数对不上，不会自愈，禁止下单直到查明 |
| 连续失败 ≥ 3 轮 | critical + 自动降级 | 自动暂停买入，保护性卖出仍执行 |
| 心跳超时 10 分钟 | critical | 调度线程卡死或退出 |
| 挂单 ≥ 10 笔 | warning | 资金被持续冻结 |
| 当日熔断 | warning | 正常保护动作，非故障 |
| 告警 24h 全失败 | warning | 通知通道已失效，出事时没人会知道 |
| 告警队列丢弃 > 0 | warning | 告警产生速度超过投递速度 |
| 启动 90 秒内无心跳 | 不报 | 宽限期，避免每次部署都发一条假告警 |

## 四、故障处置

**连续失败自动降级后怎么办**
1. 打开「运行事件」面板看最新事件里的错误原文；
2. 处理根因（通常是模型网关或行情源故障）；
3. 连续 3 轮成功后自动恢复，无需手动操作；确需立即恢复用「暂停买入」开关手动切换。

**账本漂移（critical）**
1. `POST /api/v1/trading/reconcile?repair=true` 尝试修复；
2. 循环每 5 分钟也会自动修复；若事件流里出现「修复未成功」（critical），说明挂单与账本无法互证，**必须人工核对** `trading_orders` 与 `trading_accounts`，不要再次盲修。

**进程崩溃**
守护模式自动重启，重启后自动补跑：中断的循环与计划会被标记终止、跨收盘的挂单会被清理。频繁重启（uptime 总是几分钟）本身是需要排查的故障，看 `.runtime/trading-agent.log`。

**撤单失败**
事件流出现「撤单失败」时订单保持挂起、冻结不变。这是刻意设计：通道那边可能已成交，假装撤掉会造成超卖。先查通道，再手动撤销。

## 五、接实盘还差什么

账本、风控、回报、撤单的契约已全部就绪并有测试覆盖（`report_test.go`）。接真券商只需实现一个适配器：

```go
// 实现这两个接口，替换 service.broker 即可
type Broker interface {
    Name() string
    Submit(ctx context.Context, request BrokerOrder) (BrokerResult, error)
}
type CancelableChannel interface {
    Cancel(ctx context.Context, request CancelRequest) (CancelResult, error)
}
```

成交不必在 `Submit` 里同步返回：通道异步推送回报到

```
POST /api/v1/trading/reports
{"report_id":"券商回报唯一号","order_id":"本地订单号","status":"partially_filled",
 "filled_quantity":400,"price":10.5,"fee":4.2,"at":"2026-10-21T09:35:00+08:00"}
```

已由后端保证：**同一条 `report_id` 重复投递只记一次账；回报超量按本地剩余截断并告警；已收口订单再收到成交回报不改账只报警**。

接实盘前的必做清单：
1. 适配器实现 + 通道联调（建议先只读：查资金、查持仓，不下单）；
2. 决定回报投递方式（回调 or 轮询器），确保 `report_id` 全局唯一且稳定；
3. 审阅 `ChannelInfo`：`live=true` 后页面会显示「实盘通道」，但**不会**额外加锁——实盘限额应通过风控层（`RiskRules`）收紧而不是前端提示；
4. 用最小资金量真实走一轮：下单 → 部分成交回报 → 撤单失败 → 撤单成功，逐条核对事件流。

**明确不做的事**：不提供"绕过风控直接下单"的通道；不把模型输出直接变成委托——所有订单必须经过裁决层。

## 六、已知边界

- 模拟盘撮合以最新价成交，没有盘口与滑点模拟；业绩归因因此偏乐观，接实盘前请以实盘小资金数据为准。
- `positions.peak_price` 依赖行情刷新路径（账户视图 / 防守线检查），行情长期拉不到时移动止损保持上次快照，不会用陈旧价格误触发。
- 事件表无自动清理；按当前写入密度一年约几千条，SQLite 可承载，暂不做清理任务。
- 守护脚本假定单实例运行；多实例共用同一数据库不在交付范围。
- 告警冷却状态在内存里。进程重启后冷却窗口清空，若问题仍在，会立即重新发一轮告警——
  这是有意为之：重启本身要被看见，重启后问题依旧更该被看见。代价是崩溃重启循环会重复推送。
- 告警队列容量 256。满了先丢 warning，critical 会阻塞等待 2 秒再丢并写
  `event=alert_dropped`；健康条同时出现 `alerts.dropped`。丢弃数不为零说明出口太慢，换通道或降低告警频率。
- 时间线按天查询是先粗筛（SQL 时间范围 ±1 秒）再内存精确过滤。跨零点但开始于前一天的循环，
  其结束事件归到开始那天，不拆分。
- 历史数据里 2026-10-20 之前产生的被拒委托，`quantity` 已被旧逻辑置零，回放时看到的
  「买入 0 股」属于存量记录，新产生的记录不再有这个问题。

## 七、组合级防线、复核报告与变化检测

这一节记录第四批升级。四件事共享同一条判断：**该由代码做的事不要交给模型，
该省下的模型调用不要硬问一遍。**

### 7.1 组合级回撤熔断（与日亏熔断并列，不替代）

| | 日亏熔断 | 回撤熔断 |
|---|---|---|
| 基准 | 当日基准权益 | 净值历史高点 |
| 归零 | 每个交易日 | 只在人工解除或创新高时 |
| 抓的病 | 单日被打爆 | 连续阴跌的慢刀子 |
| 解除 | 次日自动失效，或人工解除 | 警戒线回到解除线下自动解除；停止线必须人工确认 |

实现：`drawdown.go` / `drawdown_store.go`，状态落 `trading_risk_state`。

- 默认阈值 **警戒 8% / 停止 12% / 自动解除 5%**，滞回避免在 7.9%↔8.1% 反复开关。
- **高点只认已确认权益**（每轮循环开始与结束时的权益、首次观察时的初始资金），
  不取盘中 tick 瞬时值——一根插针会把峰值抬高，之后正常波动被误判成回撤。
- **两档都只暂停买入，不用 kill switch**：kill switch 会连止损卖出一起拦，
  而回撤最深的时刻恰恰最需要减仓。
- **不覆盖别人的暂停**：只有理由前缀是 `drawdown.` 的那条才会被自动解除；
  日亏熔断、连败熔断、人工 kill switch 各有责任人，混成一句会让复盘找不到原因。
- **人工解除时把高点重置为现值**。不重置的话下一轮会立刻用"旧高点 vs 现值"
  重新触发同一档位，按钮等于没用；重置的语义是"人已接受这段亏损，从当前净值重新计量"，
  平仓盈亏仍在账本里，不会被抹掉。

接口：

```
GET  /api/v1/trading/risk                          回撤状态 + 总闸
POST /api/v1/trading/risk/drawdown/release         人工解除（必须给 reason）
```

健康检查新增 `drawdown` 字段，触及任一档位时产生 `drawdown.warn` / `drawdown.stop` 事件，
并进入 `issues`；解除产生 `drawdown.release`（即使 info 也外发——
人收到"出问题了"，最想知道的下一件事是"好了没有"）。

### 7.2 计划级风险复核报告

`riskreview.go`，随计划落库（`plan.risk_review`）。它回答的是
**"这一整套方案整体安全吗"**，而裁决回答"这笔单为什么被拒"。

- 六类检查：总闸、市场状态、回撤档位、止损覆盖、单票上限、单笔风险、
  行业集中、总仓位、现金底线，最后一条是执行结果。
- 每条带 **role**：`PROPOSE`（模型提了什么）/ `EVIDENCE`（调研查到什么）/
  `VETO`（代码否掉了什么）/ `DECIDE`（代码决定了多少）/ `EXECUTE`（账本落成了什么）。
  这套词汇借自多智能体编排，但这里不是五个模型，而是五个"谁有权做这件事"的槽位。
- **只读**：不改订单、不改状态、不产生冻结。它一旦开始否决，就会与守卫形成两套口径，
  复盘时无法判断哪一套生效了。被守卫拒掉的订单不参与比例计算，否则会算出"复核超限"的假结论。
- `GET /api/v1/trading/plans/{id}` 直接返回；前端在裁决面板上方单独成块渲染。

### 7.3 时间线权限链标注

`timeline.go` 的每条记录带 `role`：计划 = `PROPOSE`、裁决 = `DECIDE`、
**被拒委托 = `VETO`**、正常委托与成交 = `EXECUTE`。纯展示层，不改变任何判定。

### 7.4 变化检测（P2-9）：没变就不问模型

`change.go`。自动循环最短 30 秒一轮、一天最多 40 轮，而行情是分钟级跳的：
三分钟内价格只动 0.05%、持仓与挂单都没变时，再问一次模型得到的答案几乎必然相同。

- **必须在快照构建之后判定**。用"距上次多久"来跳过，会在行情剧烈波动时正好漏掉最该问的一轮。
- 指纹包含：行情（价格两位小数）、持仓（数量/可卖/冻结/成本）、现金与冻结、
  在途挂单、**近期被拒记录及次数**、市场状态、候选池。时间戳、延迟、token 一律不进指纹。
- 集合先排序再入哈希：行情源返回顺序经常变，不排序会让检测永远不生效。
- 窗口 **20 分钟**；只对**定时轮次**生效（`skipOnNoChange` 由自动循环注入），
  人工触发必须真的问一次模型，否则按钮看起来像坏了。
- 指纹**只在模型调用解析成功后才记录**：失败时记录会把一次超时变成接下来 20 分钟静音。
- 跳过时计划落 `status=skipped`、返回 `ErrNoMaterialChange`，自动循环记成**跳过而非失败**；
  失败率不应因为省钱而虚高。

### 7.5 已知边界（本批新增）

- 高点按"已确认权益"记录，因此**盘中创新高后回落**不会被计入回撤基准；
  这是为了避免插针误报，代价是对"日内最高点回撤"不敏感。
- 回撤阈值目前是代码内默认值（8/12/5），不随交易风格切换；不同风险偏好需要同一套阈值，
  否则"稳健"账户会在同样的市场里比"激进"账户更早被熔断，无法横向比较。
- 复核报告里的行业集中度取自本轮决策后的暴露，**不包含卖出后的再平衡**：
  它描述的是"下单后"的静态组合，不是"全部成交后"的终态。
- 变化检测的基线在内存里，进程重启后第一轮必然调用模型。

## 八、把「承诺」变成可执行：第五批升级

前四批解决的是"系统能不能自己跑"，这一批解决的是**"它说的话算不算数"**。
模型在计划里写下的失效条件、预期期限、置信度，此前都只是文本——
写得再具体，也没有任何代码读过第二遍。这一批把它们全部接进判定链路。

### 8.1 失效条件可执行化（P0-3）

`invalidation.go`。模型可以给结构化对象，也可以继续写一句中文；
两种形态都能落成一组成员：`price_below` / `price_above` / `deadline_days` / `sector_flow` / `note`。

中文也能解析：`跌破 9.5 则离场` → `price_below=9.5`，
`5 个交易日内不兑现` → `deadline_days=5`。**兼容字符串不是宽容，是必需**——
提示词改一次，历史计划里的字符串仍然是字符串，只认对象会让旧数据的条件静默消失。

守卫的执行方式与止损刻意不同：

| | 止损 | 失效条件 |
|---|---|---|
| 含义 | 价格到线了 | 论点不成立了 |
| 力度 | 清仓 100% | **减仓 50%** |
| 次数 | 每次触价都执行 | **同一持仓只自动执行一次** |

三条边界写死在代码里：只减仓不清仓（失效条件写错的概率远高于止损线写错）；
`auto_reduce_at` 由账本在成交时写入，防止一次误判在四轮里把仓位砍到零；
`sector_flow` **不参与自动判定**——守卫在盘中拿不到板块资金序列，
判不了的事不假装判得。

### 8.2 止损冷静期（P0-4）

`cooldown.go`。两个由来已久的问题：止损后下一轮同一只票又在候选池里，
现价刚好比成本低一点，模型给出"回调到位"的建议；或者同一板块连亏两笔，
第三笔仍然通过所有单票与行业额度检查——因为仓位是空的。

- **标的级**：止损类离场后 4 小时内禁买同一标的；
- **行业级**：同行业当日累计 2 次止损后，当日禁买该行业任何标的。

约束**从平仓记录推导**，不另建表：再存一份就有两个真相来源，
某天对不上时没人知道该信哪个。约束随快照落库（`snapshot.cooldowns`），
三个月后仍能回答"当时为什么不让我买"。

只有 `stop_loss` / `hard_stop` / `trail_stop` 三类会触发冷却。
把止盈和模型主动离场也算进来，冷静期会变成"卖出即禁买"。

### 8.3 ATR 自适应防守线（P1-6）

`atr.go`。固定百分比止损对波动率一视同仁：同样 -7%，对日波动 1.5% 的银行股
是"真出事才触发"，对日波动 5% 的题材股是"正常呼吸就触发"。

- 买入时校正：距离 `< 1.2 ATR` 放宽到 `2.2 ATR`，`> 3.5 ATR` 收到 `3.5 ATR`，
  缺失按 `2.2 ATR` 兜底；**一律受 `MaxStopLossPercent` 约束**——
  ATR 只决定"多紧算合理"，不决定"能亏多少"。
- 持仓时追踪：`现价 - 2.5 ATR`，**只上移不下移**，且要求至少抬高 0.5% 才写库。
  `SetStopLoss` 的 `WHERE stop_loss_price < ?` 把"不下移"放在 SQL 层，
  不依赖调用方自觉（ATR 追踪与人工修改可能同时发生）。
- 没有日线数据时**什么都不做**，不用固定百分比假装算过。
  画像缓存 30 分钟：防守线每 15 秒看一次盘，不缓存会为每只持仓重复拉日线。

### 8.4 时间止损与论点跟踪（P1-5）

持仓上现在留三样东西：`thesis`（为什么买）、`invalidation`（什么情况算错）、
`expected_days`（多久该有结果）。它们跟着持仓走而不是跟着计划走——
计划会过期，持仓还在，"当初为什么买"不能靠翻三个月前的计划来回答。

时间止损由守卫执行：超过 `1.5 × 预期交易日` 后，浮亏则清仓，浮盈不足 2% 则减半，
浮盈超过 2% 不动（让盈利单跑）。自然日折算成交易日按 `5/7` 放大，
不接交易日历——一份没更新的休市表会在春节后把所有持仓判成"超期"。

### 8.5 置信度定价（P1-7）

`confidenceFactor`：`< 0.45` 打 0.7 折，`< 0.55` 打 0.9 折，其余不打折。
**只在明显低置信区动手**：0.6–0.8 几乎是模型的默认值，区分度极低，
对所有值打折等于施加同一个系数，反而看不出差别。真正有信息量的是
"低于 0.5 还硬要买"——那往往意味着它在凑数。

`0` 不罚：归一化后 0 表示"没填"，而不是"极度不确定"。
位置在单票上限校验**之后**：先判断目标是否越界，再打折；
反过来的话，25% 的建议打成 17% 就"合法"了。

### 8.6 记忆自动注入（P1-8）

`memory_prompt.go`。此前记忆只有一条通路：模型主动调 `recall_trades`——
实际跑下来它几乎不调，手里已经有四十行行情表，"再查一次历史"最容易被跳过。
系统记了几百条教训，却从不影响下一次决策。

现在改成"不问也给"：按同标的（+3）、同行业（+2）、同市场状态（+1）打分，
30 天内 +2、90 天内 +1，取前 8 条。**超过三个月且不是同一只票的记忆直接丢弃**——
行业与市场状态三个月就换一轮，旧结论套上来往往是错的。

只给事实不给倾向：每条是"某天、某只票、什么结果、当时的理由"，
不写"所以这次要小心"。

### 8.7 撮合真实化（P2-10）

`broker.go` 的 `PaperBroker` 补齐三个"回测漂亮、实盘做不到"的来源：

- **滑点**：默认 8bp，方向永远对自己不利（买入上滑、卖出下滑），且被限价封住。
  反方向的滑点等于内幕信息，只存在于想让曲线好看的实现里。
- **部分成交**：金额越大越难一次吃完（30 万以内全额、100 万以内 80%、再往上 50%）。
  比例由订单 ID 的 FNV 哈希决定，**同一订单多次撮合得到同一结果**——
  用随机数会让回放不可复现，"这次为什么只成交 60%"就永远解释不清。
- **涨跌停不成交**：涨停的买单、跌停的卖单保持挂单。真实市场那一刻没有对手盘，
  按现价成交会让收益凭空多出一截；保护性卖出必须能显示"止损触发了但卖不出去"。

### 8.8 策略回放沙盘（P2-11）

`sandbox.go` + `POST /api/v1/trading/plans/{id}/sandbox`。
拿一份历史计划的快照与模型建议，换一套风控阈值重新裁决，逐笔列出差异。

三条约束：**纯读**（不写订单、不冻结资金，否则沙盘与真实账本再也分不开）；
**只换阈值不换输入**（行情、持仓、现金、建议全部沿用当时那一份，这是控制变量）；
**差异必须逐笔列出**（只给"总仓位 62% → 71%"没有用，要看哪一笔被放行、哪一笔被砍小）。

时间用当时的裁决时刻而不是 now：冷静期与失效条件都以那一刻为准，
用 now 会让"当时在冷静期内"的单在回放里变成可买。

### 8.9 事件驱动临时轮次（P2-12）

`event_trigger.go`。定时间隔在平静行情里是浪费，在剧烈行情里是延误：
一只重仓票 40 秒跌 5%，等到下一轮定时循环才处理，损失已经发生。

tick 每 15 秒看一眼异动，命中就立刻发起一轮。三条限制让它比定时器更克制：

- 同一只票每天只触发一次（日内跌幅持续成立时不会反复触发）；
- 两轮之间至少 6 分钟（大于默认定时间隔的两倍）；
- 每天最多 6 次。

触发条件：单票权重 ≥ 3% 且相对昨收跌 ≥ 4%；或组合权益 15 分钟内跌 ≥ 1.5%。
**没有昨收就不判断**——用成本价替代算出来的是"持仓浮亏"，
而浮亏到 -4% 时往往早已被止损线接走。

### 8.10 已知边界（本批新增）

- 失效条件的 `sector_flow` 只回灌提示词，**不参与自动减仓**：守卫拿不到板块资金序列。
- 冷静期窗口按**自然时间**算（4 小时），跨越午休时实际只覆盖约 3 小时交易时间。
- ATR 追踪的 `2.5 倍` 对所有标的相同，没有按"是否盈利"分档；
  一只深亏的票也会被上移止损，方向上是更早离场，属于保守的一侧。
- 部分成交比例只与订单金额档位有关，**没有考虑真实盘口深度与成交额占比**，
  它是一个"让大单不一定全成"的粗模型，不是冲击成本模型。
- 事件通道的权益基线在内存里，重启后前 15 分钟不判断组合级异动。
- 沙盘用的是**当前代码的规则实现**：如果规则代码本身改了，回放的历史计划
  会按新实现重算，两者差异里混合了"阈值变化"与"实现变化"。

## 九、补齐评估清单的剩余缺口（第六批）

上一批交付后又按 `docs/trading-agent-upgrade-review.md` 逐条对账，发现四处
"清单里有、代码里没有"的缺口。这一批把它们补齐，并把四处偏离写清楚。

### 9.1 工具带从 7 个扩到 12 个（P0-1）

原状：只有资金流、行业强度、成分股、日线、个股详情、横向对比、历史记忆七件，
**全部是"当下价格结构"，没有一条回答"为什么涨"**。模型被要求写事实依据，
手上的事实只有涨幅与成交额，thesis 只能退化成"资金流入 + 涨幅居前"。

新增五个（`tools_market.go`），数据全部来自仓库已有能力，没有引入新依赖：

| 工具 | 回答什么问题 | 数据来源 |
| --- | --- | --- |
| `search_news` | 这只票/这个词最近有什么消息 | `NewsProvider` + `StockNewsSearchProvider` |
| `get_announcements` | 有没有业绩预告、减持、问询 | `MarketOverviewProvider.MarketAnnouncements` |
| `get_billboard` | 这波是谁在做（机构还是游资） | `MarketBillboardDetail` |
| `get_market_context` | 现在该不该进攻 | 指数 + 本轮认知的涨跌家数 |
| `get_margin_balance` | 杠杆资金在进还是退 | `MarketMarginSeries` |

接入方式与资金流/日线完全同构：`SetMarketIntel` / `SetNews` 可选注入，
缺了就报"数据源未配置"，绝不返回空白数据。适配层在
`httpapi/trading_tools_wiring.go`——交易侧只声明自己用到的四个方法，
行情总览加方法不会牵连交易编译。

两处刻意的诚实标注：新闻只有标题，输出里写明"未核实正文，当线索而不是结论"；
两融是**全市场口径**，输出里写明"不能用来判断个股"。
关键词检索还会报"在最近 N 条市场新闻里匹配到 M 条"——只说 0 条，
模型会推出"这件事没有新闻"的错误结论。

调研规则同步加了一条：理由只有"资金流入 + 涨幅居前"时，必须去查公告/新闻/龙虎榜，
查不到就写"未查到"，不许用板块涨幅顶替个股原因。**步数上限没有动**（仍是 4 步）：
加到 12 个工具后，问题不是工具不够用，而是要在 4 步里排好优先级；
放宽步数等于每轮多一次模型往返（约 +20% 调研成本），值不值要等实盘数据说话。

### 9.2 置信度校准（P1-7 的后半段）

原状：置信度已经参与仓位定价（`confidenceFactor` 会打折），但**没有任何校准统计**。
等于把一个未经验证的自评数字直接放大成资金暴露。

新增 `GET /api/v1/trading/calibration`（`calibration.go`）：
按 `<0.3 / 0.3–0.5 / 0.5–0.7 / 0.7–0.9 / ≥0.9` 五桶统计真实胜率、平均自评、
平均盈亏、偏差（胜率 − 自评）与 Brier 分数。

三条口径上的克制：

- **flat 不进胜率**。把"没赚没亏"算成失败会系统性压低胜率，
  进而让系统误判自己过度自信。
- **置信度 0 视为"未填"**。保护性卖出写 0 是刻意的（`guard.go`），
  那类样本根本不该进入校准。
- **不足 30 笔不下结论**，不足 8 笔的桶不点名。五笔里错三笔是 40% 还是 60%，
  换个顺序就变了。样本够了才把结论写进提示词经验段，并说明"置信度会被折算成仓位上限"。

### 9.3 上一轮调研结论复用（P1-8 的缺口）

原状：记忆会自动注入，但**上一轮查到的结论没有回灌**。同一个板块的资金流，
模型可能连续三轮各查一次，每次都是一次模型往返。

`prior_research.go` 从最近一份计划的调研记录里提取"查了什么 → 看到了什么首行事实"，
压进本轮提示词（`### 上一轮你已经查过的事实（可能已过期，引用前复核）`）。

四条边界：只取 30 分钟内的、只搬工具看到的事实不搬模型想买什么（搬判断会自我强化）、
最多 4 步且总量 700 字、失败的步骤不搬。

标题行会被跳过：工具文本第一行几乎总是"板块资金流（concept）："，
直接取第一行会让复用段里出现四条一模一样的标题——那等于没复用。

### 9.4 移动止损启动门槛与宽度 ATR 化（P1-6 的剩余部分）

原状：上一批只把**买入止损距离**和**止损上移**做了 ATR 化，移动止损的
启动门槛（4%）与回撤宽度（6%）仍是全局固定值。

现在按波动率缩放（`guard.go`）：

- 启动门槛 = clamp(1.5 × ATR%, 2%, 8%)
- 回撤宽度 = clamp(2.5 × ATR%, 3%, 12%)
- 没有 ATR 时退回 4%/6%，**不猜**——一只票没有日线，说明我们对它的波动一无所知

后果举例：成本 10、峰值 12、现价 11.2（回撤 6.67%）——
ATR 1% 的银行股该走（宽度 3%），ATR 5% 的题材股不该走（宽度 12%）。
这正是"同一套参数对前者永远等不到启动、对后者开盘就被洗出去"的解。

`ATRPercent` 只给**持仓**算，不覆盖全候选池（几十只票全拉日线会把一轮计划拖慢几十秒）；
也**刻意不进变化检测指纹**——ATR 每天都在变，算进指纹会让"什么都没变"永远不成立，
安静模式立刻失效。

### 9.5 一处测试基础设施修复

`providers/eastmoney` 的 `TestProgressiveHistoryPublishesRecentDayBeforeSlowHistory`
长期挂死，导致 `go test ./...` 跑不完。上一轮已确认它在基线提交上同样复现，
但当时只做了"排除该包"的绕过。

根因是测试自身的缓冲算错：进度回调通道容量写死 8，而窗口内每个有数据的交易日
各发布一次，节假日前后 16 个自然日里常有 11–13 个交易日——第 9 次回调就阻塞在
没人读的通道上，把整个收集循环卡死。**与业务代码无关**。
容量改成窗口长度后 1.2 秒通过，`go test ./...` 现在可以完整跑。

### 9.6 本批已知边界

- `get_margin_balance` 是**全市场口径**，仓库里没有个股融资余额数据源；
  它只能判断杠杆资金整体进退。
- 新闻只有标题与时间，没有正文；"利好/利空"的判断仍由模型做，系统不校验。
- 龙虎榜的席位名称来自上游，`institution` 标记是**分类**不是身份确认。
- 校准用的是 `trading_memory` 而不是重新解析平仓单：两处各算一遍是分歧的开始，
  但这也意味着**记忆没同步的平仓不进校准**（`POST /trading/memory/sync` 负责补齐）。
- `Position` 的 `entry_regime` / `entry_confidence` 在**第十批**才补上（见 10.3）：
  上一批以"计划里已有 regime"为由没加，事后证明这个理由不成立——计划会被清理，
  而持仓还在，复盘时只有持仓能回答问题。
- 上一轮调研复用只覆盖**同一份计划记录内**的步骤；如果某一轮没发起调研
  （模型不可用），这一段为空，不会去翻更早的计划。

## 十、按验收判定条件复核（第七批）

上一批交付后，我又拿 `docs/trading-agent-upgrade-review.md` 的**验收判定条件**
逐条对账。结论是：清单里有六处，代码里的实现与写下来的判定条件不一致
（功能"有"，但不是清单要求的那一个）。这一批全部按判定条件改齐。

### 10.1 撮合滑点改为按成交额分档（P2-10）

清单要求：`<5000 万 → 0.3%`、`5000 万–3 亿 → 0.15%`、`>3 亿 → 0.05%`；
单笔不超过当日成交额的 0.5%，超出部分成交。

原实现是**固定 8bp** + 按名义金额 30 万/100 万打折，两个参数都是自创的。
后果很具体：一只日成交 3000 万的票，8bp 滑点意味着"500 万的单能轻松吃掉"，
而真实情况下它连成交额 0.5% 的 15 万都吃不下。这正是 P2-10 要堵的
"业绩系统性偏乐观"。

现在：`QuoteView` 增加 `Turnover`（当日成交额），滑点按档位取，
流动性上限按 `成交额 × 0.5%` 截断（整手向下取整）；**成交额缺失按最冷档 0.3%**——
"数据源没给"不等于"流动性很好"。

### 10.2 仓位系数改为线性 + 增加 ATR 定价项（P1-7）

清单写的是 `0.5 + 0.5 × confidence`，再乘 ATR 调整项；原实现是 0.7/0.9 的
步进函数，且完全没有 ATR 项——置信度只有"罚/不罚"两态，0.54 与 0.56 差一个断崖。

现在：线性系数 + `clamp(2.5 / ATR%, 0.55, 1)`。两个系数**都只减不增**：
低波动票不加仓，加仓等于系统替模型放大杠杆，而且会把已通过单票上限的权重推到上限外。
ATR% 存进**快照**（`Snapshot.ATRs`），因为沙盘要用同一份输入重放，
现取会拿今天的波动率去重算上周的计划；它不进变化检测指纹。

提示词里把公式写出来了（硬性约束第 5 条）：模型如果以为"写多少就买多少"，
就会习惯性写满，然后每轮拿到打折后的额度却不知道为什么。

### 10.3 持仓补 `entry_regime` / `entry_confidence` / `review_count`（P1-5）

清单明确要求这三个字段。现在建仓时由订单携带入场环境（市场状态缺失时退回
模型自己写的 regime）、置信度写入持仓，**加仓不覆盖**（它描述的是最初的论点）；
`review_count` 由每轮防守线检查累加（一条 UPDATE 覆盖全部持仓，不逐只写）。
提示词持仓行会显示「建仓环境 / 当时置信度 / 已复核 N 轮」。

### 10.4 计划差异回灌（P0-2 的第二段）

P0-2 要两段：`RecentBlocks`（上一批已做）与 `LastPlanDiff`（此前完全没做）。
现在每轮比较"上一轮候选池 → 本轮候选池"：谁掉出、谁新进、上一轮建议买过的票
还在不在池子里。24 小时窗口，每类最多列 6 只，排序稳定。
只搬事实，不做"所以该买什么"的推断。

### 10.5 大盘工具补情绪周期（P0-1 的剩余部分）

`get_market_context` 此前只有指数与宽度，缺清单要求的"情绪周期阶段"。
现在接入 `marketemotion`（窄接口 + 适配器，交易域不依赖人气模块），
输出阶段、情绪分、置信度、数据日，并写明"阶段不能替代对个股的判断"。
空库时明说"返回空"，不让模型把缺失当成中性。

### 10.6 事件通道补板块资金流转负（P2-12 的剩余部分）

清单三类触发器，此前做了两类（单票跌幅、指数/组合跌幅），缺"板块资金流转负"。
现在补齐，并把单票阈值从 4% 对齐到清单的 **5%**。

实现上有三个约束：资金流是外部接口，取数间隔 5 分钟（跟着 15 秒 tick 打
等于一天几千次请求）；判定线是主力净占比 < −1%（净额为负但占比 −0.1% 属于抖动）；
板块名按包含关系匹配（持仓存的是行业大类，资金流给的是板块全名），
命中多条取**最差**的一条——挑最好看的那个来自我安慰最没意义。

### 10.7 一个真 bug：内存账本会串库

`OpenStore(":memory:")` 用纳秒时间戳当库名。Windows 的时间片粒度可能粗到毫秒级，
同一个测试里连续创建两个内存库会拿到**同一个名字**，而 `cache=shared` 会让它们
共享同一份数据——表现为"两个独立账本互相看见对方的计划"，且只在特定时序下出现。

这就是前两批里那次"无法复现的 httpapi FAIL"最可能的来源。现在库名带进程内自增序号。

### 10.8 定价不能把建议打成"买不起"

改完线性公式后立刻在实盘遇到反例：一笔 5% 的建议，置信度 0.62（×0.81）
叠加 ATR 4.75%（×0.55）后只剩 2.23%，2229 元买不起一手 30 元的票，
`below_lot` 把整笔建议作废——计划变成"模型提了、系统什么都没做"，
状态还是 failed。

这不是风控变严，是定价越界了：**定价的目的是"别买太多"，不是"别买"**。

现在：定价把"原本买得起一手"的建议压到不足一手时，按最小一手执行并留一条
`sizing.min_lot` 裁决；模型自己只要了不到一手（原目标 < 一手金额）时不兜底——
那是它的判断，系统替它放大几倍等于把仓位管理的责任接过来了。
一手仍受单票上限约束：连一手都超过上限的贵票，照旧拦下。

### 10.9 本批已知边界

- 滑点分档只按**当日累计成交额**，没有区分时段：开盘 5 分钟的 3000 万和
  收盘前的 3000 万，冲击成本并不一样。要细化需要分钟级成交额，当前数据源没有。
- ATR 定价项只在**买入**时用；持仓的加减仓不再按波动率重估。
  理由是持仓的退出由止损/失效条件管，重复定价会让仓位在同一轮里被两次调整。
- `review_count` 是**轮次计数**，不是"有效复核次数"：行情缺失的那一轮不会计数，
  但一轮里同时检查 7 只持仓，每只都 +1，两者不可直接比较。
- 计划差异只比较候选池与买单标的，不比较**权重变化**：权重差异已经由
  变化检测指纹和沙盘覆盖，再写进提示词会让模型把"额度变了"误读成"判断变了"。
