# 持仓防守线与复盘（P3 + P4）

这两个阶段合成一次交付的原因很直接：**防守线产生卖出成交，卖出成交才是复盘的原子事实**。
先做复盘等于对着未实现盈亏编故事，先做防守线而没有复盘则无法回答"止损位设得对不对"。

---

## 一、P3：持仓防守线

### 1.1 账本新增第三条不变量

P2 冻结的是钱，P3 必须冻结股数。没有它，同一个持仓可以被两笔卖单各卖一次：
两笔都通过"可卖数量"校验，成交时第二笔才发现不够——而那时它已经占了一个挂单位置。

三条不变量现在是：

| # | 不变量 | 维护点 |
|---|---|---|
| 1 | `account.reserved_cash == Σ 未成交买单冻结额` | `reserveTx` / `settleReservationTx` / `ReleaseOrderReservation` |
| 2 | `cash - reserved_cash >= 0` | `reserveTx` 的条件更新 |
| 3 | `position.reserved_quantity == Σ 未成交卖单剩余股数` | `reserveSellQuantityTx` / `settleSellReservationTx` / `adjustReservedQuantityTx` |

对账（`ReconcileReservations`）两条都查：资金按挂单重算，股数逐标的比对。
`repair=true` 时一并回写。有挂卖单却没有持仓，单独报错——那是必然成交失败的孤儿单。

口径统一为 `Position.Sellable() = available_quantity - reserved_quantity`，
风控、提示词、防守线三处都用它，不再各自读 `Available`。

### 1.2 防守线自成一条执行路径

`guard.go` 里的判断与模型无关，全是数字比较：

| 顺序 | 触发 | 动作 | 触发码 |
|---|---|---|---|
| 1 | 现价 ≤ 止损价 | 清仓 | `stop_loss` |
| 2 | 浮亏 > 账户硬止损（默认 10%）且该持仓无有效止损线 | 清仓 | `hard_stop` |
| 3 | 现价 ≥ 止盈价 | 按阶梯卖（默认 40% / 40%） | `take_profit_1`、`take_profit_2` |
| 4 | 浮盈 ≥ 4% 且从最高价回撤 ≥ 6% | 清仓 | `trail_stop` |

顺序不可交换：止损优先于止盈（同时满足只可能是数据异常，按最坏处理），
硬止损优先于移动止损（硬止损是买入时的承诺，不能被"还没回撤够"覆盖）。

为什么必须独立于模型：

1. 模型会超时、会返回空建议、会说"再看看"。止损不能依赖一次成功的 API 调用。
2. 买入时写下 −7%，到 −7% 不执行，那条线就只是装饰。
3. 复盘需要干净的因果：亏在止损上说明入场或止损位错了；亏在"没止损"上说明系统有病。

边界同样明确：

- **不看市场状态**：恐慌里更该执行止损，而不是因为"市场不好"而豁免；
- **不看 `pause_buying`**：那只停买入；
- **看 `kill_switch`**：全停就是全停；
- **不调模型**：一轮 `RunProtective` 不产生任何 token 费用。

### 1.3 止盈后止损上移到成本价

第一级止盈成交时，`reduce_count+1` 且 `stop_loss_price = max(现止损, 成本价)`。
止盈的目的不是多赚一点，是**把剩下那部分变成不会亏的交易**。
`reduce_count` 必须落库：不记住"减过几次"，每次触价都会再卖一次，最后清仓在最不该清的时候。

### 1.4 连败熔断终于装上弹

P2.4 时 `stop_streak` 是"已安装未装弹"，界面上是虚线。现在它接上了：

- 保护性止损成交且 `RealizedPnL < 0` → `stop_streak + 1`；
- 任何盈利平仓 → 归零（"连续亏损"必须真的连续）；
- 达到 3 笔 → `breaker = stop_streak`，同时按下 `pause_buying`。

只统计保护性离场：模型主动卖出亏了钱说明模型判断错，不是"止损被反复打穿"，
用同一根计数会把两种问题混成一个熔断。

写入用 `Store.AdjustStopStreak` 的原子加减，而不是"读出来 +1 再写回"——
两笔同时成交时后者会丢计数，而连败熔断的准确性全在"连续"二字上。

### 1.5 触发但卖不掉，必须说出来

T+1 当日买入不可卖时，防守线会记 `guard.no_sellable` 而不是静默跳过：

> `301487.SZ 已触发止损，但可卖 0 股不足一手（已解禁 0 股、已挂卖单占用 0 股），本轮无法执行`

`ProtectiveRun.Triggered` 统计"触发次数"（含卖不掉的），`Created` 统计"真正生成的订单"。
只数订单会把"止损到了却卖不了"记成"没有触发"，而这恰恰是最需要被看见的一类事实。

## 二、P4：复盘

### 2.1 只认已实现平仓

一笔卖出成交记一条 `ClosedTrade`，而不是把一轮持仓合并成一条：
分批止盈的每一批成交价不同，合并成加权平均之后，"第一次止盈的位置选得对不对"
这个问题就永远回答不了了。

字段里 `EntryPrice` 取自卖出时刻的持仓均价（含买入费用分摊），
`PnL = (卖出价 − 均价) × 股数 − 本笔卖出费用`，与账本口径完全一致。
持仓天数按 `opened_at` 到成交时间算；旧数据没有 `opened_at` 就记 0 天并保留空值，不猜。

### 2.2 数字全部由代码算

`ReviewFacts` 里没有一个字段来自模型：

- 平仓笔数、胜负、胜率、盈亏比、平均盈亏、平均持有天数；
- 按离场原因分类：止损 / 硬止损 / 移动止损 / 止盈 / 模型离场；
- 裁决层：建议数、通过数、拦截数、拦截代码分布；
- 循环层：总轮次、完成、跳过、失败；
- 模型成本：平均耗时、当日 token。

权益口径与日亏熔断同源（当日基准权益 → 当日最后一轮收盘权益），
不用"现在这一刻"的快照算历史某天。

### 2.3 样本下限 30，不给就是不给

`Lesson.WinRate` 是指针类型，不是 float：

> 10 笔交易的 60% 胜率不是"胜率 60%"，是"还看不出来"。

样本 < 30 时字段整体不出现，文案明确写"样本不足 30 笔，胜率不予显示"。
`0%` 与"还不知道"在复盘里是两条完全相反的信息，用一个 float 表达必然有一个会被误读。

维度只保留两个：**离场原因**与**行业**。按日期或按价格档位切分，
每组只剩两三笔，除了制造噪声没有别的用途。

### 2.4 幂等

`trading_reviews` 主键是 `(account_id, trading_day)`，重算覆盖不新增。
复盘不是流水，是"这天到底发生了什么"的定稿。

自动生成时机：收盘后 15:05 起，`Autopilot.maybeReview` 每天跑一次
（15 秒一次的 tick 从 15:05 到午夜有上千次机会，没有幂等判断会重算上千遍）。

### 2.5 经验回流到提示词

`Service.Experience` 取最近 30 个交易日的平仓记录，按样本量排序取前 8 条，
作为提示词的「四、历史经验」段。同时写死一句边界：

> 经验只说明过去发生过什么，不构成对本轮的指令。每一笔仍要独立判断，止损纪律不因历史统计而放宽。

不写这句，模型会把"上次止损的都亏了"理解成"这次不要止损"。

## 三、接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/trading/positions` | 持仓（含可卖、冻结、防守线、浮盈） |
| POST | `/api/v1/trading/positions/{symbol}/protection` | 人工设置止损/止盈（填 0 表示不设） |
| POST | `/api/v1/trading/protective/run` | 立即检查防守线，不调模型 |
| GET | `/api/v1/trading/closed-trades` | 最近已实现平仓 |
| GET | `/api/v1/trading/reviews` | 最近复盘 |
| POST | `/api/v1/trading/reviews/run` | 生成/重算某日复盘（幂等） |
| GET | `/api/v1/trading/reviews/{day}` | 按交易日读取 |

## 五、已知边界

1. **T+1 无法绕过**：当日买入的仓位当天不会被防守线卖出，系统会明确记录"触发但不可卖"。
   这不是缺陷，是 A 股规则；把它藏起来才是缺陷。
2. **止盈阶梯固定 40/40**：剩余 20% 交给移动止损。参数化留到 P5 与实盘通道一起做，
   现在改它没有足够的成交样本支撑。
3. **行业归因依赖买入时的 `sector`**：旧持仓没有这个字段，会归入"未知行业"。
   不回溯猜测，猜出来的归因比没有归因更糟。
4. **复盘只统计当日**：跨日窗口只用于经验（30 个交易日），不做跨日胜率曲线。
   曲线要有意义，至少需要几十个交易日的数据。
