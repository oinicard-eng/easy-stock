# P2.2 市场认知与候选池

这一层回答两个问题：**现在该不该下注**，以及**下注在什么上**。

两者都不交给模型。理由写在最前面：如果让模型判断"今天是牛市还是熊市"，
同一个输入两次调用会得到两个答案，那么后面所有的仓位预算都失去基准，
复盘时也无法归因——分不清是"判断错了"还是"那天模型心情不同"。

## 一、数据口径：认知与选股必须同源

`cognition` 与 `universe` 共用同一份 `StockCatalog` 全市场快照（约 5500 只，含价格、涨跌幅、5 日涨幅、成交额、行业、概念）。

这不是省一次请求，而是避免自相矛盾：

```
如果大盘状态来自指数接口、候选池来自股票目录接口：
  指数接口 14:59 的数据说"退潮"
  目录接口 15:01 的数据说"87% 个股上涨"
  → 模型读到两个相反的结论，无从判断该信哪一个
  → 无论它选哪个，复盘时都无法说清依据
```

同源之后，广度指标与候选池永远描述同一时刻的同一个市场。

`eastmoney.StockCatalog` 自带 3 分钟 TTL 缓存，正好对应循环频率，不需要再加缓存层。

## 二、市场认知：广度指标与状态判定

### 广度指标

只统计有有效价格的标的（停牌不计入，否则会稀释指标）：

| 指标 | 含义 |
| --- | --- |
| `advance_ratio` | 上涨家数 / (上涨 + 下跌)，反映赚钱效应的扩散程度 |
| `median_change` | 涨幅**中位数**，不是均值 |
| `limit_up` / `limit_down` | 涨停/跌停家数，按各自的涨跌停幅度判定 |
| `total_amount` | 全市场成交额合计 |

用中位数而非均值，是因为均值会被少数涨停股拉高：9 只涨 0%、1 只涨停，
均值 +1% 看起来不错，中位数仍是 0——后者才符合大多数人的体感。

### 涨跌停判定

按标的各自的幅度判断，容差 0.15 个百分点：

```
主板 10%、创业板/科创板 20%、ST 5%、北交所 30%
|涨幅 - 幅度| <= 0.15  →  判定为涨停
```

容差来自交易规则本身：涨停价按前收盘四舍五入到分，所以前收 3.01 元的主板股票
涨停价 3.31 元、实际涨幅 9.97%。不设容差会漏计，设太大（如 0.5）会把 9.7% 误判为涨停。

**只有 ST 按 5% 判定这一条最容易写错**：一只 ST 股涨 5% 就是涨停，
若统一按主板 10% 判断，会漏掉所有 ST 涨停，退潮日反而看不出情绪崩塌。

### 状态与仓位预算

判定顺序从极端到常态，因为"跌停成片"与"涨停成片"同时出现时应按更危险的一侧处理：

| 状态 | 判定条件（任一满足） | 仓位预算 | 含义 |
| --- | --- | --- | --- |
| 恐慌 `panic` | 跌停 ≥ 30 家，或中位数 ≤ -3%，或上涨占比 ≤ 15% | 20% | 无差别抛售，禁止开新仓 |
| 退潮 `ebb` | 上涨占比 ≤ 35%，或（涨停 < 15 家且中位数 < -0.5%） | 40% | 赚钱效应消失 |
| 亢奋 `euphoria` | 涨停 ≥ 80 家且上涨占比 ≥ 70% 且中位数 ≥ 1.5% | **65%** | 情绪过热 |
| 上行 `uptrend` | 上涨占比 ≥ 60% 且中位数 ≥ 0.5% | 85% | 可正常建仓 |
| 震荡 `range` | 以上都不满足 | 55% | 方向不明 |
| 数据不足 `unknown` | 有效样本 < 500 只 | 0% | 不允许开仓 |

**亢奋的预算刻意低于上行**（65% < 85%）。线性地"越热越重仓"是最常见的新手错误：
情绪最热时买入成本最高、回撤最快，而"这次不一样"的念头也最强。

样本少于 500 只时返回 `unknown` 且预算 0。这是安全默认值：
数据源异常或非交易时段时，宁可不动，不可据残缺数据下注。

### 实测

2026-10-20 收盘：

```
全市场 5496 只有效行情（6 只停牌）
上涨 3727 只、下跌 1646 只、平盘 123 只，上涨占比 69.4%
涨停 54 家、跌停 6 家，涨幅中位数 +0.96%、平均 +1.24%
成交额合计 14664 亿元
→ 判定「上行」，仓位预算 85%

行业强度前列：机器人 +3.38%（16/16 上涨）、半导体 +3.04%（156/174）、
              耐火材料 +3.03%、计算机软件 +2.82%（237/263）……
行业强度末位：林业 -1.69%、煤炭 -2.29%、船舶与海洋装备 -3.01%
```

## 三、候选池：先排除，再打分

### 硬性排除（无论涨得多好）

| 规则 | 理由 |
| --- | --- |
| 无有效价格 | 停牌，无法定价 |
| 名称含 ST / 退 | 涨跌停仅 5%，退市风险无法用技术面衡量 |
| 股价 < 2 元 | 面值退市风险 + 流动性差 |
| 单手金额 > 总资产 25% | 10 万账户买 500 元的股票，一手就是半个仓位，没有仓位管理可言 |
| 北交所 | 30% 波动 + 流动性差异，单独一套规则 |
| 已涨停 / 接近涨停 | 买不进；即使买到也是成本最差的位置 |
| 已跌停 / 接近跌停 | 不接下落的刀 |
| 成交额 < 门槛 | 无法从容进出，滑点会吃掉全部收益 |

### 成交额门槛的自适应

默认 5000 万元。缩量行情（节前、极端缩量）下固定门槛会把全市场筛空，
而"没有候选"并不代表"没有机会"，只代表门槛不合适。因此逐级放宽：

```
5000 万 → 3000 万 → 1500 万 → 500 万
```

降级时 `degraded = true`，提示词里也会说明，避免模型误以为当天全是垃圾股。

### 打分：五个维度，每维都做"过热惩罚"

| 维度 | 权重 | 说明 |
| --- | --- | --- |
| 动量 | 30 | 当日涨幅，倒 U 型 |
| 趋势 | 25 | 5 日涨幅，超过 25% 开始扣分 |
| 流动性 | 20 | 成交额的对数分位 |
| 行业强度 | 15 | 所属行业在强度榜的分位 |
| 相对强度 | 10 | 当日涨幅减去行业中位，识别板块内龙头 |

**动量分是倒 U 型，这是整个打分最关键的取舍**：

```
-5% → 5 分      0% → 40 分      6% → 100 分      涨停位 → 30 分
```

当日涨幅 3%~6% 是最优区间（启动初期），超过 6% 后按"距离涨停还有多远"线性扣分。
大多数选股逻辑线性追涨，把仓位集中到已经涨完的标的上；
真实交易员知道最肥的一段是启动初期，不是涨停板。

这里踩过一个坑：最初写成"超过涨停幅度的 60% 直接归零"，
主板 10% 时该阈值正好是 6%，与上一档 `change <= 6` 重叠，
结果涨 6.01% 的股票得分 15、涨 0.8% 的得分 48——涨得多反而被当成利空。
现在改为按距离涨停线性递减。

### 分散约束：数独立风险来源，不是数代码个数

这是实测后补上的一条，也是这一层最有价值的改动。

某日按纯分数排序，15 只候选里 **11 只是科创板**，且集中在半导体与机器人。
每只单独看都合规，合起来是同一个风险敞口——板块回调时一起跌。

第一版修法是"同行业最多 3 只"，但立刻失效：数据源的行业名很细，
前 12 只分属「半导体、电子元件、消费电子设备、电子设备制造、计算机软件」
五个不同行业，每个刚好卡在 3 只内，实际上全是电子周期。

因此加了 `sectorOf` 把细分行业归入大类（16 个大类），并按大类计数：

```
电子 3 · 计算机 3 · 机械 3 · 汽车 3 · 周期 3 · 医药 3 · 电力设备 3 · 其余各 1
```

同时限制同板块占比 ≤ 45%。修复后实测：科创板 9 / 主板 10 / 创业板 9。

归并刻意粗放：宁可把两个弱相关的行业并成一类（少选几只），
也不要把同一个风险拆成两类（以为分散了、其实没有）。

未选满 30 只时 `capped = true`，明确说明是被分散约束截断，而不是没找到票。

### 入选理由

每只候选都带 3~5 条带数字的理由，直接进提示词：

```
- 688165.SH 埃夫特（系统评分 79.5）：当日 +5.62%，处于启动区间（未过热）；
  5 日 +5.24%，中期趋势向上；成交额 1.57 亿，现价 14.55 元；
  行业「机器人」平均 +3.38%，行业强度第 1/103 名
```

模型读到的不是一串代码，而是"为什么是它"；人也能核对系统有没有乱来。

### 排除项也要记录

`Exclusions` 按原因聚合被排除的标的数，并保留 2~3 个样本：

```
成交额低于 5000 万元，流动性不足        1364 只
板块不在可选范围（北交所）               329 只
ST 或退市风险警示                       195 只
已涨停或接近涨停，无法从容买入            52 只
股价低于 2 元                            37 只
同板块候选已达上限（避免单一风险）       2775 只
同类风险敞口已达上限（电子）              633 只
```

没有这一段，用户只会觉得"我的股票怎么没被选中"，进而不再信任系统。

## 四、仓位预算如何真正生效

认知层给出的 `risk_budget_percent` 不只是一个展示数字，它同时进入两处：

1. **提示词**：告诉模型本轮总仓位上限（如"上行 → 85%"）
2. **风控**：`BuildOrders` 里取 `min(市场预算, 风控上限)` 作为实际上限

但提示词只是约束，不是保证。模型会给出合计 120% 的目标权重。
若放任到下单阶段，资金不足会让靠前的几笔占满额度、后面的被逐笔缩减，
相对权重被扭曲成"先到先得"。

因此风控加了一层等比缩放：超出上限时按同一比例缩减全部买入，
保持模型给出的相对权重。缩减后不足一手的订单标记为 rejected 并说明原因，
不做向上取整——向上取整会让总仓位重新突破上限。

## 五、可观察接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/trading/market` | 市场状态、广度指标、行业强度、仓位预算 |
| GET | `/api/v1/trading/universe?limit=30` | 候选池、入选理由、排除项 |

两者与生成计划时用的是同一套计算，**看到的即决策依据**。

计划记录里同时保存 `snapshot.market` 与 `snapshot.board`，
事后复盘可以还原"当时系统看到了什么、为什么选这些"。

## 六、自动选股的触发条件

`POST /api/v1/trading/plans` 的 `watchlist` 留空即自动选股（或显式传 `auto_universe: true`）。

三种情况会 fail 并写明原因，而不是拿空池去问模型：

| 情况 | 行为 |
| --- | --- |
| 未配置全市场行情源 | 直接拒绝，提示显式提供标的 |
| 全市场快照拉取失败 | 计划标记 failed，保留已算出的市场认知 |
| 市场判定为恐慌 / 数据不足 | 计划标记 failed，候选池为空并说明原因 |

显式指定 `watchlist` 时不做自动选股，且市场认知拉取失败不阻塞计划——
否则一次行情源抖动会让用户手动指定的计划也无法生成。

## 七、已知限制

- 行业归并靠关键词表，新行业名可能落到默认分支（不归类，按原名计数），需要维护。
- 5 日涨幅来自数据源，不含更长的趋势判断；20 日/60 日均线尚未接入。
- 不做基本面筛选（估值、业绩预告、解禁），这些是 P3 之后的事。
- 候选池只保证"在这批数据下最优"，不保证跑赢指数；它的价值在于可解释与可复现。
- 板块上限与行业上限叠加时可能选不满 30 只（实测 28 只），这是刻意的取舍。
